The Transone-OptimusP is a hardware translation bridge integrated directly into the Analog Network‑on‑Chip (ANoC) and the binary bus fabric. It enables seamless, real‑time cooperation between the 192 (or more) Transone analog cores and 4 binary RISC‑V cores, while also serving as the gateway for the Transone GPU to render binary game frames and for developers to run legacy software. The bridge is designed to be transparent at the hardware level: the binary cores see the Transone resources as memory‑mapped coprocessors, and the Transone cores see binary memory as a set of special analog ports. All conversions happen in a single clock cycle on either side, with zero firmware overhead.

---

## 1. Top‑Level Architecture

The OptimusP sits at a crosspoint between the ANoC 2D mesh (carrying 8‑column multi‑wire words) and a 256‑bit wide binary AXI4 bus connected to the 4 binary cores’ L2 cache coherence fabric. It contains:

- **Voltage‑to‑Bit (V2B) Engine** – captures analog column voltages and converts them to binary integers/floating‑point.
- **Bit‑to‑Voltage (B2V) Engine** – generates precise multi‑wire voltage clusters from binary data.
- **Direct Memory Access (DMA) Cluster** – moves data between binary DRAM and Transone register files or GPU buffers without core intervention.
- **Command Queue Manager** – holds work descriptors submitted by binary software, dispatches them to Transone cores or the GPU.
- **Translation Lookaside Buffer (TLB)** – maps binary virtual addresses to Transone physical core/column targets.
- **Streaming Converters** – for graphics, converts vertex/index/texture data on‑the‑fly as it is read from binary memory, feeding the Transone GPU.

All blocks operate with the strict four‑state voltage discipline on the Transone side, and standard CMOS logic levels on the binary side. Isolation is provided by Deep Trench Isolation and level‑shifter rings.

---

## 2. Voltage‑to‑Bit (V2B) Engine – ADC Matrix

The V2B engine samples a full 8‑column Transone word (e.g., from a register or ALU output) and produces a binary representation. It must handle the unique multi‑wire encoding where each column’s total voltage is a decimal digit 0–9, constructed from 2 V and 1 V parallel wires.

### Column ADC Design

For each column, the V2B uses a **flash ADC** with 10 high‑speed comparators whose thresholds are set at 0.5 V, 1.5 V, …, 8.5 V. The column’s wire bundle is connected to a precision summing node that drives the comparator inputs. Because the summing is passive, a unit‑gain buffer first isolates the column to avoid loading. The comparators are chopper‑stabilized to reduce offset and drift, and they output a 10‑bit thermometer code. A fast logarithmic encoder converts this to a 4‑bit binary digit (0–9) in under 3 ns.

For signed values, column 7 (the sign/magnitude indicator) is sampled with a polarity comparator: if the column carries a negative voltage (State −1), the sign bit is set. The ADC output is combined with the sign to produce a signed binary word.

All 8 columns are digitised in parallel. The 8×4‑bit digits are packed into a 32‑bit BCD‑like integer (or converted to a 32‑bit binary number via a simple binary‑to‑BCD converter inside the OptimusP). Optionally, the engine can normalise to IEEE‑754 single‑precision floating point using a dedicated arithmetic block, but primary transfers use integer or fixed‑point.

**Performance:** Total conversion latency = 12 ns (buffer + comparator + encoder). The result is latched and ready for the binary bus in the same 50 ns Transone cycle.

### Multi‑Word Burst Mode

For bulk data, the V2B can sample successive Transone words on the ANoC using a burst clock, achieving 20 M words per second (one per 50 ns Transone cycle). The 256‑bit binary bus can accept up to 8 words per burst, effectively transferring 256 bits of binary data per Transone cycle – fully saturating the ANoC bandwidth.

## 3. Bit‑to‑Voltage (B2V) Engine – DAC Matrix

The B2V engine receives binary data and drives the multi‑wire Transone column buses with exact voltages. It must generate the parallel 2 V and 1 V wires per column without producing any illegal intermediate voltages.

### Column DAC and Wire Encoder

For each column, the B2V receives a 4‑bit digit value (0–9) from the binary word. A high‑speed decoder converts this digit into a set of enable signals:

- Number of 2 V wires = floor(digit/2)
- One 1 V wire enabled if digit is odd

Each enable signal controls a precision analog switch (pass‑transistor) connecting a master voltage rail (2.0 V or 1.0 V) to the corresponding output wire. The voltage rails are generated by ultra‑low‑noise, high‑current op‑amp buffers referenced to an on‑chip bandgap reference trimmed to within 0.1%.

To guarantee no overlap or intermediate voltages, the decoder uses break‑before‑make switching and the output wires are clamped by fast Schottky diodes to −1 V and 2 V. The entire column driver settles to within 1% of target voltage in 15 ns, well within the Transone 50 ns cycle.

**Signed values:** If the binary sign bit indicates negative, the B2V engine injects a −1 V (State −1) onto the sign column (following the Transone signed‑magnitude convention) and drives the remaining columns with absolute value digits.

### Parallel Column Drive

All 8 columns are driven simultaneously. The B2V engine receives a full 32‑bit word (or 64‑bit with sign extension) and generates the 8‑column multi‑wire bundle in one shot. This allows the binary core to write a single binary register and have the Transone core see the analog data on the next ANoC clock edge.

**Streaming Mode:** For graphics, the B2V can convert a stream of binary vertex data into Transone GPU format on the fly. It uses a FIFO buffer and a state machine to pack binary floating‑point coordinates into 4‑column fixed‑point Transone words, applying scale factors as configured by the GPU driver.

## 4. DMA Cluster and Memory‑Mapped Interface

The OptimusP exposes a set of memory‑mapped registers to the binary cores, making Transone resources appear as a coprocessor with shared memory. Key regions:

- **Transone Core Register Windows:** Each of the 192 Transone cores’ register files are mapped to a 4 KB address range. A binary write to a register triggers an immediate B2V conversion and writes to the target core’s register. A read triggers a V2B conversion from that register. This allows direct binary access to Transone core state.
- **Transone GPU Command Queue:** A ring buffer in binary DRAM holds command packets (draw, dispatch, set shader). The OptimusP’s DMA engine reads these packets, converts any pointers/parameters via B2V, and pushes them to the Transone GPU’s command processor through the ANoC.
- **Bulk Data Transfer Descriptors:** For large datasets (textures, vertex buffers), the binary driver writes a DMA descriptor containing source binary address, destination Transone GPU memory region, and conversion type. The OptimusP’s DMA cluster performs the data movement entirely in hardware, using B2V streaming to write to the GPU’s analog memory or V2B to read back framebuffers.

### Zero‑Copy Translation Buffers

To eliminate copying, the OptimusP includes a **Translation Lookaside Buffer (TLB)** that can remap pages in binary physical memory directly to the ANoC address space. When a Transone core accesses a specially encoded address, the TLB triggers an on‑the‑fly B2V/V2B conversion of the cache line being fetched, effectively letting Transone cores “read” binary RAM directly. This is limited to data‑only accesses and uses a small page table maintained by the binary OS.

## 5. Command Queue Manager and Interrupt Handling

Binary software submits work via the command queue. The OptimusP contains a dedicated microcontroller‑class sequencer that:

1. Polls the ring buffer head pointer (in binary memory).
2. Reads command descriptors, which are 64‑byte packets specifying operation type (e.g., “RUN_TRANSONE_TASK”, “DRAW_TRIANGLES”).
3. For “RUN_TRANSONE_TASK”, the OptimusP locates the Transone‑native Silex program in binary memory, converts the program image (using V2B on the instruction words) and writes it to the target Transone core’s instruction cache, then asserts a start signal.
4. For GPU commands, the descriptor contains transformed vertex buffer addresses and shader programs. The DMA cluster streams the data into the GPU’s unified memory, and the command manager signals the GPU’s dispatch unit.
5. Upon completion, the Transone core or GPU sends an ANoC completion packet (a special voltage‑encoded message). The OptimusP receives it, converts it to a binary interrupt, and writes a completion event to the binary core’s interrupt controller.

All command translation is pipelined; multiple commands can be in flight across different cores and GPU pipelines.

## 6. Integration with the Transone GPU for Binary Games

The 4 binary cores run the game logic and a thin graphics driver. When a draw call (e.g., Vulkan API) is invoked, the driver:

- Allocates Transone GPU memory for vertex/index/constant buffers through the OptimusP’s memory manager.
- Writes the draw command descriptor into the ring buffer, pointing to binary‑side buffers holding vertices in single‑precision float.
- The OptimusP’s streaming B2V converts the float coordinates to 4‑column fixed‑point Transone format (e.g., scaling to 0–9999). The converted vertex data is written directly to the GPU’s vertex buffer memory over the ANoC.
- Shader programs (compiled from HLSL/GLSL to Silex GPU assembly offline) are already in Transone format; the descriptor simply points to the Transone‑native shader binary.
- The GPU’s analog rasteriser and fragment shaders execute the draw call entirely in the Transone domain, producing a framebuffer.
- To display, the framebuffer is read by the V2B engine (or a dedicated display converter) and output to a standard HDMI/DisplayPort PHY. This conversion runs at 60 Hz with line‑buffered streaming.

Thus, any binary game that uses a standard graphics API can run on the Transone system with full hardware acceleration, while the 192 Transone cores remain free for physics, AI, or other native Silex tasks.

## 7. Developer Environment: Silex and Legacy Compilation

The OptimusP is also the target for two compilation flows:

- **Legacy (Python, C++, Rust):** A standard GCC/LLVM toolchain compiles to the binary RISC‑V cores. To access Transone acceleration, the code links against `libtransone`, a userspace library that communicates with the OptimusP driver. The library provides functions like `transone_vector_add()`, which internally formats the command descriptors and triggers the DMA. The OptimusP handles all conversion transparently.

- **Native (Silex):** The Silex compiler generates Transone‑native 8‑column instruction words. These programs run directly on the 192 Transone cores. The binary OS can launch a Silex program by loading it into Transone memory via the OptimusP and setting a program counter. Inter‑process communication between Silex tasks and binary tasks uses shared memory regions with the OptimusP converting data as needed.

This dual‑path approach allows the Transone platform to be a fully capable general‑purpose computer with an unparalleled analog acceleration path.

## 8. Physical Implementation and Performance

The OptimusP is implemented as a hard macro on the chip, measuring about 4 mm² in a 5 nm process. It contains ~2 million binary transistors (for control logic, decoders, FIFOs) and ~50,000 precision analog comparators/switches. It runs from the binary cores’ 2.5 GHz clock domain for the digital side, while the analog converters are clocked by the Transone 20 MHz domain with asynchronous handshake.

**Latency:**  
- Single‑word V2B conversion: 12 ns + 50 ns Transone cycle = 62 ns end‑to‑end.  
- Single‑word B2V conversion: 15 ns + 50 ns = 65 ns.  
- Streaming bulk conversion: 20 M words/s sustained, enough to feed the Transone GPU’s vertex pipeline at full rate.

**Power:** The OptimusP consumes approximately 1.2 W when all channels are active, thanks to aggressive clock gating and the use of dynamic comparators that only draw current during transitions.

The Transone-OptimusP thus completes the hybrid chip: 192 analog Transone cores, a 16k‑core GPU, 4 binary RISC‑V cores, and a hardware bridge that makes them all work together as a single seamless platform. The result is a machine that natively runs all existing binary software while unlocking a new class of analogue‑native performance through Silex.
